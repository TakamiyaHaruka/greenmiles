# GreenMiles 项目文档

**航司绿色里程生态商城 — 从需求到落地的全记录**

---

## 一、项目背景

### 1.1 业务痛点

传统航空公司会员的里程面临两大问题：

- **零碎里程难兑换** — 兑换机票门槛太高，小礼品缺乏吸引力，大量里程沉睡
- **碳足迹认知空白** — 旅客越来越关注绿色出行，但缺乏将"认知"转化为"行动"的工具

### 1.2 产品构想

**GreenMiles** 是一个轻量级的绿色里程生态商城：旅客输入航班信息即可看到本次飞行的碳排放量，并用里程兑换环保商品与碳抵消服务，实现"飞得越多，绿得越深"的正向循环。

核心体验旅程：**Reveal（揭示碳排）→ Offset（采取行动）→ Proof（携带证明）**

### 1.3 项目定位

Demo / PoC（概念验证）。本地运行或内部演示，不接入真实支付与真实用户数据。核心目标是验证"碳足迹可视化 + 里程绿色兑换"这一产品假设的可行性。

### 1.4 技术栈

Next.js 16 + React 19 + Tailwind CSS 4 + shadcn/ui + SQLite + Zustand + Zod + JWT

### 1.5 开发方式

全流程使用 BMad Method v6.7.1，由 AI Agent 协助完成需求分析、架构设计、UX 设计、Story 拆分和代码实现。

| 文档 | 内容 | 作用 |

项目初期没有完整的 PRD，只有一份初步的产品构想和上述两份参考文档。PRD、Architecture、UX Design、Epics & Stories 都是在 BMad 流程中通过多轮对话逐步产出的。

这种"轻输入、重讨论"的方式，是 BMad Method 的核心理念之一——**不要求你一开始就有完美的文档，而是通过 Agent 的追问帮助你把模糊的构想变成结构化的需求**。

## 三、讨论业务和需求文档时，使用了哪些 BMad 方法论

### 3.1 阶段一：产品定义（bmad-product-brief）

**做了什么：** 通过 PM Agent 的引导，明确了产品的核心定位、目标用户和价值主张。

**关键讨论：**
- 读者是谁？→ 外部演示介绍用
- 一句话定位是什么？→ "让飞行碳足迹可见，让闲置里程变绿"
- 核心体验是什么？→ Reveal → Offset → Proof

**产出物：** Product Brief（产品简介，1-2 页，用于外部演示）

### 3.2 阶段二：需求分析（bmad-prd）

**做了什么：** PM Agent 与我进行了多轮对话，从模糊的产品构想逐步推导出结构化的需求文档。

**关键讨论节点：**

**（1）产品定位之争：商城 vs 计算器**

> 最初我认为碳排放计算器是产品主体。PM Agent 引导分析——碳排放计算本身不具备持续使用价值，用户算完一次就离开了。真正能让用户反复回来的是商城。
>
> **决策（#13）：** 商城是主体，计算器是商城内的工具模块。

**（2）用户场景推演：Reveal → Offset → Proof**

> PM Agent 引导我走了一遍完整的用户旅程：输入航班 → 看到碳排 → "这个数字很大，我该怎么办？" → 下方直接出现推荐商品 → "用 1200 里程就能抵消？" → 一键兑换 → 获得券码。
>
> 这个推演帮我明确了"碳排放数字永远不孤立出现，旁边必有兑换 CTA"的设计原则。

**（3）商品选择与兑换逻辑**

> 初始方案只做植树公益。讨论后决定首批 4 种商品，覆盖 4 种兑换逻辑：券码、二维码、碳抵消数据、待发货状态。

**（4）碳排放公式**

> PM Agent 追问：公式考虑哪些因素？系数从哪来？最终确定三因子公式（距离 × 机型系数 × 舱位权重），系数来源 ICAO 标准。

**（5）余额不足的处理**

> 初始方案是余额不足时隐藏商品。讨论后改为仅置灰结算按钮 + 提示差额——让用户看到全部商品，但清楚知道自己差多少。

**产出物：**
- PRD 文档（含 19 条决策日志）
- 碳排放计算规范
- 决策追溯记录

### 3.3 阶段三：架构设计（bmad-create-architecture）

**做了什么：** Architect Agent 引导我进行关键技术选型的讨论，每个决策都有明确的理由和权衡。

**关键讨论：**

| 决策点 | 选项 | 最终选择 | 理由 |
|--------|------|----------|------|
| 数据库 | SQLite / PostgreSQL | SQLite | PoC 零外部依赖 |
| 碳排计算 | 前端 / 后端 | 前端 | 纯计算，支持实时响应 |
| 认证方案 | JWT / Session | JWT + httpOnly cookie | Edge Runtime 兼容 |
| 状态管理 | Zustand / Redux | Zustand | 轻量，TypeScript 友好 |

**产出物：** Architecture 文档

### 3.4 阶段四：UX 设计（bmad-create-ux-design）

**做了什么：** UX Agent 引导我打磨交互细节，从宏观的页面流程到微观的组件状态。

**关键讨论：**

- 商品详情：独立页面 vs Sheet 抽屉 → 选 Sheet，保持用户上下文
- 购物车：Dialog 弹窗 vs 侧边栏 → 选 Dialog，轻量操作
- 碳排放可视化：圆环图 + 直觉化比喻（"相当于一棵树 X 天的吸收量"）
- 余额不足：置灰按钮 + 红色小字差额提示

**产出物：** UX Design Specification

### 3.5 阶段五：Story 拆分（bmad-create-epics-and-stories）

**做了什么：** 将 PRD 和 UX Design 拆分为 4 个 Epic、15 个 Story，每个 Story 使用 BDD 格式编写 Acceptance Criteria。

**Epic 拆分逻辑：**

```
Epic 1: 基础设施（项目初始化 → 数据库 → 注册 → 登录 → 导航栏）
         ↓
Epic 2: 碳排放计算（引擎 → UI → Banner）
         ↓
Epic 3: 绿色商城（商品列表 → 详情 → 购物车 → 结算 → API）
         ↓
Epic 4: 会员控制台（订单历史 → KPI 看板）
```

**产出物：** Epics & Stories 文档（15 个 Story，每个含 BDD 格式 AC）

### 3.6 阶段六：实施就绪检查（bmad-check-implementation-readiness）

**做了什么：** 检查 PRD、UX、Architecture、Epics 之间的对齐关系，确保没有遗漏或矛盾。

**产出物：** Implementation Readiness Report

### 3.7 阶段七：开发实施（bmad-sprint-planning + bmad-dev-story）

**做了什么：** 通过 Sprint Planning 生成进度追踪文件，然后按 Story 顺序逐一实现。

**执行节奏：**
```
Sprint Planning → Story 1.1 → 1.2 → ... → 4.2 → 全部完成
```

**15 个 Story 全部 done。** 产出完整的可运行应用。

## 四、从需求到落地的感受（测试视角）

### 4.1 以前做测试，需求是"别人给的"

作为测试工程师，过去的工作模式是：产品经理写好 PRD，开发做完代码，然后交给我测试。我拿到的需求文档已经是"成品"，我的工作是在成品上找 bug。

这种模式下，我对需求的理解是**二手的**——我看到的是最终版本，不知道中间经历了哪些讨论、哪些妥协、哪些被放弃的方案。当我在测试中发现"这个逻辑不太对"的时候，往往已经晚了——改起来成本很高，或者干脆被告知"需求就是这样"。

### 4.2 这次不一样：我从需求讨论开始参与

这次用 BMad Method 做 GreenMiles，最大的不同是**我全程参与了需求讨论**。

PM Agent 不会替我做决定，但它会追问：
- "你说的碳排放计算器，它的公式是什么？"
- "用户算完碳排之后呢？你希望他做什么？"
- "余额不足的时候，是隐藏商品还是提示差额？"

这些追问逼着我把模糊的想法变成具体的设计。以前我写需求文档，经常写着写着就发现"这个细节我还没想清楚"。这次有 PM Agent 帮我系统性地暴露这些盲区。

### 4.3 需求讨论中最有价值的三个点

**（1）用户场景推演**

PM Agent 让我走了一遍完整的用户旅程：从输入航班到获得券码。这个过程帮我发现了"碳排放数字不能孤立出现"这个关键设计原则。如果直接写功能列表，我可能会把"碳排放计算"和"商城兑换"写成两个独立功能，忽略它们之间的引导关系。

**（2）决策日志**

PRD 过程中产生的 19 条决策记录，是我这次最大的收获。以前做项目，很多决策做完就忘了为什么，后面维护时反复纠结。这次每个"为什么"都有记录，比如"为什么余额不足时只置灰不隐藏"——因为用户需要看到全部商品才能做出比较。

**（3）BDD 格式的 Acceptance Criteria**

以前写测试用例，经常需要自己从需求文档中"翻译"出测试场景。这次 Story 的 AC 直接用 Given/When/Then 格式，测试用例可以直接从 AC 派生，减少了需求理解偏差。

### 4.4 跑完全流程的体会

从需求讨论到代码实现，跑了完整的 BMad 四个阶段。最大的感受是：**需求阶段花的时间是最值得的**。

PRD 阶段花了最多时间（多轮对话、反复推敲），但后面的 Architecture、UX Design、Story 拆分都因为有了清晰的 PRD 而变得顺畅。如果 PRD 阶段偷懒，后面的每个阶段都会多出很多返工。

另一个体会是：**AI Agent 是放大器，不是替代品**。它不会替你思考产品定位，但会帮你把想法变成结构化的文档。关键在于——你得知道自己要什么。

## 五、测试工程师如何利用 BMad 进行需求研究与探索

### 5.1 BMad 对测试工程师的核心价值

作为测试工程师，BMad Method 最大的价值不是"帮我写代码"，而是**帮我从源头理解需求**。

传统模式下，测试工程师在需求阶段的参与度很低——PRD 是产品经理写的，架构是开发设计的，测试只能在最后阶段"找 bug"。BMad 改变了这个模式：**测试工程师可以全程参与需求讨论，在需求阶段就发现潜在的问题**。

### 5.2 具体的应用场景

**（1）用 bmad-prd 参与需求讨论**

测试工程师可以在 PRD 阶段就参与讨论，从"可测试性"的角度提出问题：
- "这个碳排放公式的边界值是什么？距离为 0 怎么办？距离为负数怎么办？"
- "余额不足时，是扣到 0 还是拒绝交易？"
- "并发兑换同一个商品，库存怎么处理？"

这些问题在需求阶段提出，比在测试阶段发现要便宜得多。

**（2）用 BDD 格式的 AC 派生测试用例**

BMad 的 Story 使用 BDD 格式（Given/When/Then）编写 Acceptance Criteria。测试工程师可以直接从 AC 派生测试用例，减少需求理解偏差：

```
AC: Given 用户余额不足，When 点击结算按钮，Then 按钮置灰 + 显示差额提示
→ 测试用例：设置用户余额为 500，商品价格为 1200，验证按钮状态和提示文案
```

**（3）用 Decision Log 做回归分析**

PRD 阶段的决策日志（19 条）是测试回归分析的宝贵资源。当需求变更时，可以回溯决策记录，理解变更的影响范围：
- "这个决策当初为什么这么做的？"
- "改变这个决策会影响哪些 Story？"
- "哪些测试用例需要更新？"

**（4）用 bmad-code-review 做代码审查**

测试工程师可以用 Code Review 工具从测试角度审查代码：
- 错误处理是否完整？
- 边界值是否覆盖？
- 事务是否保证原子性？

### 5.3 后续计划

| 方向 | 具体行动 |
|------|----------|
| 测试前置 | 在 PRD 阶段就参与需求讨论，从可测试性角度提出问题 |
| AC 派生 | 建立从 BDD AC 到测试用例的标准转化流程 |
| 回归分析 | 利用 Decision Log 做变更影响分析 |
| 自动化测试 | 使用 bmad-qa-generate-e2e-tests 生成 API 和 E2E 测试 |
| 持续集成 | 将测试集成到 BMad 的 Story 完成流程中 |

### 5.4 对 BMad 工具的改进建议

| 建议 | 说明 |
|------|------|
| 增加 QA Agent 自动触发 | Story 状态变为 done 时，自动建议运行 QA 测试 |
| 测试覆盖率追踪 | 在 sprint-status.yaml 中增加测试覆盖率指标 |
| 回归测试建议 | 代码变更时，自动识别受影响的 Story 和测试用例 |
| 测试数据管理 | 种子数据的版本化管理，支持测试环境隔离 |
